# dead-mans-switch 実装進め方ガイド

本ドキュメントは、AIエージェントおよび開発者が本プロジェクトを段階的に安全に実装・テスト・デプロイするための手順書です。

---

## 1. 人間側での事前準備（外部サービス）

1. **Cloudflare Email Routing の宛先承認 & 送信元アドレス確認**
   - Cloudflare Dashboard > **Email Routing** > **Destination addresses** で送信先メールアドレス（`KIN_EMAIL_ADDRESS`）の受諾（Verify）を済ませておく。
   - 自身の所有ドメインに属する送信元アドレス（例: `noreply@yourdomain.com`）を `SENDER_EMAIL_ADDRESS` として決めておく。
2. **Web Push 用 VAPID 鍵ペアの生成**
   - `npx web-push generate-vapid-keys` を実行し、生成された Public / Private Key を手元に控えておく。
3. **Cloudflare Zero Trust (Access) アプリケーション設定**
   - Cloudflare Dashboard > **Zero Trust** > **Access** > **Applications** にて新規 Application を作成。
   - Application Path: `your-worker-domain.workers.dev/checkin`
   - Policy: Allow / Emails: `OWNER_EMAIL_ADDRESS`（本人メールアドレスのみアクセス許可）を設定。

## 2. 実装運用・コミットルール ＆ リカバリ手順

### 2.1. フェーズごとの検証 ＆ コミット提案タイミング

1. 各フェーズ（フェーズ 1〜4）のタスク完了ごとに `pnpm exec tsc --noEmit` および `pnpm test` を実行して合格を確認する。
2. チェックリストの条件を満たした段階で、ユーザーへ「フェーズ X の実装完了と型チェック・テスト合格」を報告し、Git コミットの実施許可を仰ぐ。
3. ユーザーの確認・承認後に Conventional Commits 形式のコミットを実行する（勝手な自動コミット/push は禁止）。

### 2.2. 仕様不整合・バッティング発生時のリカバリ手順

1. **問題の検知と即時停止**: 実装中に型定義の相違・ライブラリ制約・エッジ環境の挙動差異など仕様書との不整合を発見した場合、独断で隠蔽や辻褄合わせの修正を行わず作業を一時停止する。
2. **原因特定とユーザー報告**: 不整合の原因、影響範囲、および提案する解決策（仕様書の更新案等）をまとめてユーザーへ報告・協議する。
3. **仕様書とコードの同期修正**: 解決策の同意を得た後、コードの修正と同時に `docs/REQUIREMENTS.md` および `docs/ARCHITECTURE.md` を更新する（DoDの徹底）。
4. **安全な復元**: 大幅な修正を行う場合は `git stash` や退避を行っておき、いつでもテストが合格する安定状態へ戻せるように担保する。

## 3. 段階的実装ロードマップ

`docs/ARCHITECTURE.md` のディレクトリ構成に基づき、以下のフェーズ順にモジュール単位で作成・テストを行ってください。

### フェーズ 1: プロジェクト基盤の初期化 & 設定

> **[!NOTE] 既存ファイルが存在する場合の初期化手順**
> 現在のディレクトリには既存のドキュメント類（`docs/` や `README.md` 等）が Git 管理下で保存されています。
> `pnpm create hono@latest . --template cloudflare-workers --pm pnpm` を実行し、既存ファイルの上書き確認が表示された場合はそのまま実行してください。既存ドキュメントが上書きされた場合は `git checkout` または `git restore` で復元します。

- `.node-version`: 内容を `24` とした環境固定用ファイルを作成。
- `package.json`: `pnpm create hono@latest` 実行後に `"engines": { "node": ">=24.0.0" }` を追加設定。
- 依存ライブラリのインストール: `pnpm add hono mimetext web-push`
- テスト・開発環境用パッケージのインストール: `pnpm add -D wrangler vitest @cloudflare/vitest-pool-workers typescript @cloudflare/workers-types`
- `wrangler.toml`: `docs/ARCHITECTURE.md` 7章に従い、KVバインディング（`DMS_KV`）、`send_email`、`crons`、`compatibility_flags = ["nodejs_compat"]`、`assets = { directory = "./public" }`、非機密環境変数（`BASE_URL`, `WARNING_DAYS`, `DEAD_DAYS`, `WARNING_EMAIL_SUBJECT`, `WARNING_EMAIL_BODY`, `DEAD_EMAIL_SUBJECT`, `VAPID_SUBJECT`, `SENDER_EMAIL_ADDRESS`）を設定。
- `vitest.config.ts`: Vitest Workers Pool 用の設定ファイルを作成。
- `src/types.ts`: KVデータ構造（`status`, `last_active_at`, `warning_sent_at`, `dead_sent_at`, `push_subscriptions`）、`Env` 型定義を作成。

### フェーズ 3: メインロジック & API の実装 (`src/index.ts` & `public/sw.js`)

- **Service Worker スクリプト (`public/sw.js`)**:
  - `push` イベントでの通知表示 & `notificationclick` での `clients.openWindow('/checkin')` 画面起動処理を記述（※APIトークン露出防止のためトークンは保持しない）。
- **API ルーティング (Hono)**:
  - `GET /checkin`: 生存確認・ステータス表示・Web Push 登録ボタン付き HTML 画面（`DEAD` 時のロックアウト制御含む、Zero Trust 保護）
  - ※ Service Worker (`public/sw.js`) は Workers Assets により静的自動配信されます。
  - `POST /api/ping`: パッシブアクティビティ更新（`DEAD` 時は `403` 返却、認証トークン検証）
  - `POST /api/push/subscribe`: Web Push サブスクリプション情報登録（Zero Trust 保護）
  - `GET /api/status`: デバッグ・状態確認 JSON（認証トークン検証）
- **Cron Trigger 定期実行**:
  - 日次チェック（12時間マージン判定、二重送信防止・再試行ロジック、メール + Web Push 警告送信）

## 4. 環境設定 & デプロイ

```bash
# 1. KV ネームスペースの作成（出力された ID を wrangler.toml に記載）
pnpm wrangler kv:namespace create DMS_KV

# 2. シークレット環境変数の設定
pnpm wrangler secret put PING_SECRET_TOKEN          # API認証キー（必須）
pnpm wrangler secret put OWNER_EMAIL_ADDRESS        # 本人メールアドレス（必須）
pnpm wrangler secret put KIN_EMAIL_ADDRESS          # 送信先メールアドレス（必須）
pnpm wrangler secret put DEAD_EMAIL_BODY            # 死後通知本文（任意: 未設定時はデフォルト通知本文を適用）
pnpm wrangler secret put VAPID_PUBLIC_KEY           # Web Push 用 VAPID 公開鍵（必須）
pnpm wrangler secret put VAPID_PRIVATE_KEY          # Web Push 用 VAPID 秘密鍵（必須）

# 3. 本番デプロイ
pnpm deploy

# 4. 初回 Web Push 購読設定
# デプロイ後に https://<YOUR_WORKER_URL>/checkin （Zero Trust 認証をパス）へアクセスし、「通知を許可」ボタンを押す。
```
